先知道，这一阶段多了什么

第二阶段能“看商品”，第三阶段开始能“登录后买商品”。最大的变化，是系统开始修改真实数据。

你可以把项目想成一家小店：Vue 是店面，Java 是负责办事的柜台，MySQL 是记订单和库存的账本。第三阶段把三者连起来：登录 → 选择商品和数量 → 下单并扣库存 → 查看本人订单 → 模拟支付。

先记住这三句话
  1. 前端负责交互；身份、价格、库存由后端和数据库决定。
  2. 订单写入与库存扣减必须一起成功，失败就一起撤销。
  3. 请求失败可能只是回执丢了；重试同一次购买要用同一个 requestKey。

跟一笔订单，走完前后端

先串通整个过程，再进入具体方法。每层只做自己那一份工作。

  1. 页面先问：现在是谁？

    OrderPanel 挂载时调用 GET /api/v1/auth/session，拿到 user 和 csrfToken。user 为 null 就显示登录表单。

  2. 用户登录

    前端先取当前 CSRF，再 POST 用户名和密码。Java 校验密码，轮换 Session ID 和 CSRF，返回当前用户。

  3. 前端提交购买意图

    只发送 productId、quantity、requestKey。浏览器另带会话 Cookie，请求头带 X-CSRF-Token。

  4. Java 取得身份并办业务

    拦截器检查 CSRF、绑定请求身份。Controller 检查参数，Service 查数据库商品、检查幂等并开启订单事务。

  5. MySQL 写订单、扣库存

    先由唯一键确定是否是新订单，再执行条件扣减。缺货抛异常，两项修改一起回滚。

  6. 前端拿到结果

    更新订单列表，通知 App 刷新商品列表和详情库存。模拟支付时只改订单状态。

返回成功前要经过事务提交。Service 方法里的 return 先回到 Spring 事务代理；代理提交成功，Controller 才能把成功结果交出去。提交失败仍可能得到服务错误。

前端：把“收银台”接到商品页

先认识 Vue 的三个工具：ref 记状态，computed 自动判断，watch 监听变化。

App.vue 是父组件，原本管理商品列表与详情。新增的 OrderPanel.vue 是子组件，专门处理身份和订单。父组件把当前商品传进去，子组件下单成功后通知父组件刷新库存。

:product
把表达式的值作为商品参数交给子组件。详情没成功时传 null，避免对旧商品下单。
@created
监听子组件的 created 事件。这里是本项目定义的“订单创建成功”通知。

ref 像界面的记事本；在脚本中通过 .value 读写。session 记身份，quantity 记输入，orders 记订单列表。Vue 会据此更新显示。模板中通常不必写 .value。

computed 像一张自动重算的检查单：登录了吗？选了商品吗？数量是 1～100 的整数吗？现在有别的写操作吗？这些决定按钮能否点击。按钮可点不代表库存已经保留，真正下单时还要由数据库判定。

下单成功后，emit('created', productId) 触发上面的方法，重新查询列表和所选商品。void 表示这里有意不等待 Promise，并不表示请求同步完成。true 让列表刷新时保留当前商品选择。

登录：身份放在服务端，写操作再核票

Cookie、Session、CSRF 不是三个同义词。用“寄存柜和操作校验票”来理解最直接。

Session：服务端的寄存柜
Java 记住当前用户。业务接口从这里取身份，不让前端自报 userId。
Cookie：浏览器带的柜号
浏览器同源请求自动携带。页面没有把密码或 Session ID 保存到 localStorage。
CSRF token：写操作的额外校验票
前端放在 X-CSRF-Token 请求头，后端和 Session 内的随机令牌比较。它不能代替登录身份与订单归属检查。

登录前再拿一次令牌，是为了应对会话已经过期的情况。密码随这次登录请求发送；输入框内容在提交时被清空，页面不会持久化密码。

service.login 先验证用户名和密码。成功后 changeSessionId() 换掉旧柜号，signIn 同时发布新身份与新 CSRF 令牌。密码校验使用 JDK 的 PBKDF2WithHmacSHA256 和安全比较；数据库保存加盐派生哈希。

拦截器先取同一份不可变会话状态，把用户绑定到当前 request，再核对 CSRF。Controller 之后读取的是这次请求的身份快照。这样，另一标签页切成 Bob，也不会让已经按 Alice 校验的旧请求突然变成 Bob 的操作。

登录、退出、下单、支付都要 CSRF。

匿名 GET 订单会得到 401；如果匿名 POST 连令牌也没带，会先被 CSRF 拦成 403。检查顺序决定了先看到哪个错误。

退出会让旧 Session 失效，再创建新的匿名会话。当前 Session 保存在应用内存，Java 应用重启后需要重新登录。

请求层：统一发件，还要验货

TypeScript 的 interface 是说明书；网络数据进来后，运行时校验才是真正拆箱验货。

api.ts 继续复用原来的 getJson。名字虽然含 get，它现在也能发 POST，统一处理 JSON、10 秒超时、取消和错误分类。

  • method：有 post 参数就写入，否则读取。
  • Content-Type：说明请求体是 JSON；X-CSRF-Token：带操作校验票。
  • credentials: 'same-origin'：携带同源会话 Cookie；开发时浏览器访问 Vue 的同源 /api，再由 Vite 代理给 Java。
  • signal：合并取消与超时；停止等待不等于服务端停止办事。
  • cache: 'no-store'：请求不使用缓存；身份和订单响应后端也禁止缓存。

远程 JSON 最初是 unknown。即使写了 OrderView 类型，服务器仍可能返回坏结构。这里实际检查编号、数量、金额字符串、CNY 币种和两个合法状态，失败就报 INVALID_DATA，不会假装拿到了正常订单。

请求层怎样分类失败？
NETWORK / TIMEOUT
网络或读取响应体失败 / 超过 10 秒。
INVALID_JSON / INVALID_DATA
成功响应不能解析成 JSON / 能解析但不符合约定。
HTTP + apiCode
服务端返回非成功状态，再保留稳定业务码。HTML 错误页也不会掩盖原 HTTP 状态。

后端入口：只收购买信息，不收“我是谁”

Controller 接 HTTP 和参数；Service 负责业务。把两层分开，才能清楚知道规则在哪里。

下单只接受三个字段：productId 选哪件、quantity 买多少、requestKey 哪一次购买。没有 userId、单价和总价字段：身份从会话取，价格从数据库查，总额由后端算。

@RestController 让返回对象变成 JSON；@RequestBody 把 JSON 读成请求对象；@Valid 触发正整数、数量范围和键格式校验；sessions.requireUser(request) 取已绑定的请求身份，未登录就拒绝。

Service 是接口，OrderServiceImpl 是实现；@RequiredArgsConstructor 让 Lombok 生成构造器，Spring 注入所需对象。Service 仍再做一次参数防御，因为它将来可能被 HTTP 之外的调用者使用。

下单事务：一张订单和一笔扣减，一起落账

事务可以理解为“一次完整办理”：中途失败，已经做的数据库修改也要撤销。

这里沿用 Controller → Service 接口 → ServiceImpl → Mapper 接口 → XML → MySQL。Mapper 接口声明 Java 方法，XML 里的同名 id 写真正的 SQL，MyBatis 把参数绑定进去。

  1. 检查输入，先找同键旧单。存在就核对商品与数量；相同则返回原单。
  2. 从数据库取商品。复制商品名和价格，算好金额，状态设为待支付。
  3. 先插订单。让数据库唯一约束裁决是不是一次新的购买。
  4. 再条件扣库存。扣不到就抛运行时异常，插入的订单也回滚。
  5. 事务正常完成后提交。浏览器收到成功响应，再更新页面。

mapper.insert(order) 执行时还没提交。库存不足会抛 OrderAccessException，它是运行时异常，Spring 默认会回滚。于是不会留下“订单创建了，库存却没扣”的半截结果。

@Transactional 通过 Spring 代理生效，MyBatis 使用同一事务连接。本项目是同一个 MySQL 数据库内的本地事务；没有跨服务分布式事务，也没有用 Java 的 synchronized 保护所有买家。

进阶：为什么只给 create 设置 READ_COMMITTED？

两个请求可能先后查到同键不存在。唯一 INSERT 会让输家等赢家提交，然后报重复键。输家接着普通 SELECT，需要读到赢家刚提交的订单。READ_COMMITTED 让每条查询读取新的已提交快照；REPEATABLE_READ 的旧快照可能看不到赢家。

这里还依赖 InnoDB 在重复键失败时只回滚失败语句的行为。没有把整个应用的隔离级别改成 RC；RC 本身也不是防超卖措施。死锁、连接或提交失败仍可能返回服务错误，同一次意图仍应保持同键重试。

防超卖：把“够不够”和“扣多少”写进同一条 SQL

库存只剩 1 件，两个人同时买，谁都可能在旧页面看到“有货”。所以不能相信前端显示或 Java 先查的旧值。

SET available_stock = available_stock - quantity
执行真正扣减。
WHERE available_stock >= quantity
扣减发生时还得有足够库存；检查和修改在同一语句中。
影响 1 行 / 0 行
1 行说明扣成功；0 行说明没有满足条件的库存行，Service 抛缺货异常。

InnoDB 更新时锁住这条库存记录。后来的人要等待，轮到他时再用当时的库存判断。例如 A 买走最后 1 件并提交，B 再判断时库存已经是 0，扣减失败。

version 自增，不等于这里用了乐观锁。

当前 WHERE 没有比较旧 version，因此直接防超卖的是条件 UPDATE 与行锁。原库存表的非负 CHECK 约束再做兜底。

如果只在 Java 里先 SELECT 库存再判断，两个人都可能看到 1。前端限制数量、禁用按钮也只能减少误操作，不能替代数据库里的这个条件。

幂等：同一次购买，重试不能再买一遍

幂等听起来抽象，可以理解为：拿同一张取号票再来，拿回原结果，而不是再办一单。

最关键的是 requestKey ??= crypto.randomUUID()：只有当前没有键才生成。网络失败时不清空，所以不改商品和数量再点一次，还是原来的键。

数据库按 (user_id, request_key) 唯一：同一用户、同一键只能有一张订单。不同用户用同一个键互不影响。相同商品与数量返回原单，改参数却硬用原键就返回 409 IDEMPOTENCY_CONFLICT。

前面的 SELECT 只是提前省工作；两个并发请求都能查到空，最后要靠唯一 INSERT 裁决。它放在扣库存之前，重复请求才不会先扣一遍再发现重复。

键什么时候保留，什么时候换？
  • 网络错误、超时：保留；相同商品详情刷新短暂变 null：也保留。
  • 换商品、改变数量、切身份：清空；这些是新的购买意图。
  • 明确成功后清空；下一次点击可以再买一单。
  • 刷新或关闭页面：内存键会丢失，先查本人订单确认，不能盲目重新购买。

下面的“同键改数量”展示后端防御规则；正常页面监听数量变化，会主动创建新意图。

本人订单、金额与模拟支付

这三个问题都不能交给客户端自行决定：订单属于谁？当时多少钱？现在能否支付？

列表直接在 SQL 按会话用户过滤，只取最近 100 单。详情与支付都再次检查订单归属；知道别人的订单编号也不能读取或支付。当前规则：不存在返回 404，存在但不是本人返回 403，因此会暴露这个编号存在。

订单像收据，保存下单当时的商品名、单价与总额。商品以后改名改价，不会把旧收据一起改掉。总额由 Java BigDecimal 乘整数数量，JSON 通过 toPlainString() 输出十进制字符串，前端只排版。

先 SELECT ... FOR UPDATE 锁定订单，校验归属，再把待支付改为已支付。第一次更新 1 行；重复调用时订单已经 PAID，条件更新 0 行，仍返回 PAID。这里不扣库存，库存已经在下单时扣了。

当前只有 PENDING_PAYMENT 和 PAID 两种状态，所以可以这样处理。未来增加取消、退款状态时必须重新检查逻辑。模拟支付只改状态，没有真实资金、支付渠道或回调。

待支付订单也占库存。

目前没有到期取消与库存释放；刷新、关闭页面、退出登录都不会自动退回库存。

旧响应别回来覆盖新页面

取消请求，是叫浏览器别等；请求序号和身份版本，是让已经迟到的结果别写错地方。

假设 Alice 的订单请求还在路上，界面已经退出并登录 Bob。旧响应即使最后到达，也必须丢弃；否则页面可能把 Alice 的结果塞进 Bob 的界面。

AbortController
通知浏览器取消等待；不证明服务端没有创建订单。
request / listRequest
核对是不是最新一轮请求，防止旧列表覆盖新列表。
identity / identityVersion
核对当前身份有没有换代；旧账号的结果不能进入新账号界面。

clearIdentityData() 会增加身份版本、取消旧请求、增加请求序号并清空订单。写操作的 mutate() 也检查这些条件，并取消旧列表：避免支付前发出的列表，把刚显示的 PAID 覆盖回待支付。

同一页面在写操作期间禁用退出，是减少竞争的交互措施；后端绑定请求身份快照，则负责服务端的身份一致性。前端保护与后端授权各有职责。

错误翻译：记住“错在哪里”，显示时再翻译

如果报错时直接保存一句中文，切成英文后它还是中文。保存结构化错误，才能随当前语言立即重译。

后端返回稳定 code，api.ts 保留在 ApiError.apiCode；组件保存错误对象，computed 依据当前词典生成文案。切语言只重新渲染，不必重发订单请求。

Object.hasOwn 确认错误码是映射表自己登记的键，避免 toString 等继承属性误命中。未知码显示当前语言的通用 HTTP 提示；服务端 message 留作错误数据，不直接放到页面。

401 · AUTH_REQUIRED
请先登录。
401 · INVALID_CREDENTIALS
用户名或密码错误。
403 · CSRF_INVALID
会话校验失败，刷新后重试。
403 · ORDER_FORBIDDEN
不是自己的订单。
404 · ORDER_NOT_FOUND
订单不存在。
409 · INSUFFICIENT_STOCK
库存不够。
409 · IDEMPOTENCY_CONFLICT
同一个键被用于不同的购买参数。

以上为本阶段新增 7 类错误；沿用商品阶段 4 类。后端在具体处理器返回固定、安全的中文兜底，不按语言头翻译，也不泄露 SQL 或凭据。api.ts 不依赖界面词典、不主动设置 Accept-Language；浏览器可能自动携带自己的原生语言头。

UI 支持中文、英文、日文；商品名称与描述保持数据库原文，价格仍为 CNY，不换汇。本学习手册按你的要求用中文讲解。

数据库与初始化：不只靠 Java 记规矩

应用检查负责友好拒绝，数据库约束负责守住最后一道边界。

lab_user
存用户名和密码哈希；用户名唯一。
commerce_order
存用户、商品、数量、金额快照、幂等键、状态和创建时间。
UNIQUE
同一用户的同一个请求键不能产生两张订单。
CHECK
数量在 1～100，单价非负，总额等于单价乘数量，状态限定为两种。

async function getJson<T>(
  path: string,
  signal: AbortSignal,
  validate: (value: unknown) => value is T,
  post?: { body: unknown; csrfToken: string },
): Promise<T> {
  const timeoutSignal = AbortSignal.timeout(10_000)
  const requestSignal = AbortSignal.any([signal, timeoutSignal])
  let response: Response
  let text: string
  try {
    response = await fetch(path, {
      signal: requestSignal,
      method: post ? 'POST' : 'GET',
      headers: {
        Accept: 'application/json',
        ...(post ? { 'Content-Type': 'application/json', 'X-CSRF-Token': post.csrfToken } : {}),
      },
      body: post ? JSON.stringify(post.body) : undefined,
      credentials: 'same-origin',
      cache: 'no-store',
    })
    // Receiving headers does not finish the request: reading the body can fail too.
    text = await response.text()
  } catch (error) {
    if (signal.aborted) throw error
    if (timeoutSignal.aborted) {
      throw new ApiError('TIMEOUT', '商品服务响应超时，请稍后重试。', { cause: error })
    }
    throw new ApiError('NETWORK', '暂时无法连接或读取商品服务，请稍后重试。', { cause: error })
  }

  const httpMessage = `商品服务请求失败（${response.status}），请重试。`
  let body: unknown
  try {
    body = JSON.parse(text)
  } catch (error) {
    // An HTML error page must not hide the HTTP status behind a JSON error.
    throw new ApiError(response.ok ? 'INVALID_JSON' : 'HTTP',
      response.ok ? '商品服务返回了无法解析的 JSON，请刷新重试。' : httpMessage,
      { cause: error, status: response.status })
  }
  if (!response.ok) {
    const message = isObject(body) ? body.message : undefined
    const apiCode = isObject(body) && typeof body.code === 'string' ? body.code : undefined
    throw new ApiError('HTTP', typeof message === 'string' && message.trim() ? message : httpMessage,
      { status: response.status, apiCode })
  }
  if (!validate(body)) {
    throw new ApiError('INVALID_DATA', '商品服务返回的数据格式不符合约定，请刷新重试。')
  }
  return body
}

import static lab.commerce.exception.OrderAccessException.Reason.AUTH_REQUIRED;
import static lab.commerce.exception.OrderAccessException.Reason.CSRF_INVALID;

@Component
public class SessionAccess implements HandlerInterceptor {
    private static final String STATE = SessionAccess.class.getName() + ".state";
    private static final String REQUEST_USER = SessionAccess.class.getName() + ".requestUser";
    private static final SecureRandom RANDOM = new SecureRandom();

    public SessionView view(HttpSession session) {
        synchronized (session) {
            var state = (SessionView) session.getAttribute(STATE);
            if (state == null) {
                state = new SessionView(null, newToken());
                session.setAttribute(STATE, state);
            }
            return state;
        }
    }

    public void signIn(HttpSession session, UserView user) {
        // Publish identity and token atomically; readers never pair two login generations.
        session.setAttribute(STATE, new SessionView(user, newToken()));
    }

    public long requireUser(HttpServletRequest request) {
        var user = (UserView) request.getAttribute(REQUEST_USER);
        if (user == null) throw new OrderAccessException(AUTH_REQUIRED);
        return user.id();
    }

    private String newToken() {
        byte[] bytes = new byte[32];
        RANDOM.nextBytes(bytes);
        return Base64.getUrlEncoder().withoutPadding().encodeToString(bytes);
    }

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        String path = request.getRequestURI();
        if (path.startsWith("/api/v1/auth/") || path.equals("/api/v1/orders") || path.startsWith("/api/v1/orders/")) {
            response.setHeader("Cache-Control", "no-store");
        }
        var session = request.getSession(false);
        var state = session == null ? null : (SessionView) session.getAttribute(STATE);
        if (state != null && state.user() != null) request.setAttribute(REQUEST_USER, state.user());
        if (!"POST".equals(request.getMethod())) return true;
        String expected = state == null ? null : state.csrfToken();
        String actual = request.getHeader("X-CSRF-Token");
        if (expected == null || actual == null || !MessageDigest.isEqual(
                expected.getBytes(StandardCharsets.UTF_8), actual.getBytes(StandardCharsets.UTF_8))) {
            throw new OrderAccessException(CSRF_INVALID);
        }
        return true;
    }
}

@Service
@RequiredArgsConstructor
public class OrderServiceImpl implements OrderService {
    private final OrderMapper mapper;
    private final ProductMapper products;

    @Override
    @Transactional(readOnly = true)
    public List<OrderView> list(long userId) {
        return mapper.findForUser(userId).stream().map(OrderView::from).toList();
    }

    @Override
    @Transactional(readOnly = true)
    public OrderView detail(long userId, long id) {
        return OrderView.from(owned(userId, id));
    }

    private CommerceOrder owned(long userId, long id) {
        var order = mapper.findById(id);
        if (order == null) throw new OrderAccessException(ORDER_NOT_FOUND);
        if (order.getUserId() != userId) throw new OrderAccessException(ORDER_FORBIDDEN);
        return order;
    }

    @Override
    @Transactional(isolation = Isolation.READ_COMMITTED)
    public OrderView create(long userId, long productId, int quantity, String requestKey) {
        if (productId < 1 || quantity < 1 || quantity > 100 || requestKey == null
                || !requestKey.matches("[A-Za-z0-9_-]{8,80}")) throw new IllegalArgumentException();
        var previous = mapper.findByRequestKey(userId, requestKey);
        if (previous != null) return repeated(previous, productId, quantity);
        var product = products.findById(productId);
        if (product == null) throw new ProductNotFoundException();
        var order = new CommerceOrder();
        order.setUserId(userId);
        order.setProductId(productId);
        order.setProductName(product.getProduct().getName());
        order.setQuantity(quantity);
        order.setUnitPrice(product.getProduct().getPrice());
        order.setTotalAmount(order.getUnitPrice().multiply(BigDecimal.valueOf(quantity)));
        order.setRequestKey(requestKey);
        order.setStatus("PENDING_PAYMENT");
        order.setCreatedAt(LocalDateTime.now(ZoneOffset.UTC).withNano(0));
        try {
            // The unique key serializes concurrent retries BEFORE any inventory deduction.
            mapper.insert(order);
        } catch (DuplicateKeyException exception) {
            // InnoDB rolls back the failed statement only. READ_COMMITTED gives this
            // SELECT a fresh snapshot after the winner commits, without lock upgrades.
            var existing = mapper.findByRequestKey(userId, requestKey);
            if (existing == null) throw exception;
            return repeated(existing, productId, quantity);
        }
        if (mapper.deductStock(productId, quantity) != 1) {
            // Runtime exception also rolls back the just-inserted order.
            throw new OrderAccessException(INSUFFICIENT_STOCK);
        }
        return OrderView.from(order);
    }

    private OrderView repeated(CommerceOrder existing, long productId, int quantity) {
        if (existing.getProductId() != productId || existing.getQuantity() != quantity) {
            throw new OrderAccessException(IDEMPOTENCY_CONFLICT);
        }
        return OrderView.from(existing);
    }

    @Override
    @Transactional
    public OrderView pay(long userId, long id) {
        var order = mapper.findByIdForUpdate(id);
        if (order == null) throw new OrderAccessException(ORDER_NOT_FOUND);
        if (order.getUserId() != userId) throw new OrderAccessException(ORDER_FORBIDDEN);
        // Conditional transition is idempotent; no money moves in this learning simulation.
        mapper.markPaid(id, userId);
        order.setStatus("PAID");
        return OrderView.from(order);
    }
}
